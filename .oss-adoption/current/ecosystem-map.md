# Ecosystem map

Labels in this map have strict meanings: **Fact** is supported by repository or cited primary evidence; **Inference** is a synthesis of those facts; **Hypothesis** requires market evidence; **Owner choice** is a decision the maintainer must approve. None is treated as approved merely because this analysis recommends it. All external sources below were verified 2026-07-19 UTC.

## User workflow and adjacent systems

**Owner choice:** Koi owns the local control-plane path from **service exists** to **service has a stable, trusted LAN identity**. It collaborates with systems that own workload execution, filtering, remote reachability, public ingress, enterprise identity, and observability.

The recommended collaboration doctrine is simple: built-in DNS, proxy, CA, and health components are dependable zero-dependency fallbacks. When Pi-hole, Caddy, Tailscale, Smallstep, or Prometheus already owns a function, Koi should feed that specialist instead of creating a second source of truth. In public language, **“works with” means a versioned end-to-end test, an explicit ownership boundary, diagnosable failure behavior, and a reversible off-ramp**. Parsing or emitting a compatible format should be called **format-compatible** until that contract passes.

| User stage | Existing owner or workaround | Koi's role | Explicit boundary |
| --- | --- | --- | --- |
| Run a workload | Native process, Docker, Podman, VM, appliance | **Fact:** Observe or accept service metadata; Docker/Podman labels can drive announce, DNS, certificate, health, and proxy behavior | Koi is not a scheduler and does not replace Compose, Podman, systemd, or Kubernetes |
| Discover what exists | Bonjour, Avahi, application-specific scans | **Fact:** Browse, resolve, announce, lease, and retract mDNS/DNS-SD services through one cross-platform engine | Multicast discovery is local in scope; routed networks require a deliberate bridge or unicast source |
| Give it a stable name | Router DNS, hosts files, dnsmasq, Pi-hole, AdGuard Home | **Fact:** Populate a private `.internal` zone from static entries, discovery, containers, and certificate state; export hosts/dnsmasq/JSON formats | Koi should be authoritative only for its delegated private zone, not replace filtering or organization-wide DNS |
| Make the name trusted | Self-signed certs, `mkcert`, Caddy local CA, Smallstep | **Fact:** Enroll nodes, install the Koi root, issue and renew private certificates, and diagnose trust posture | Koi is not enterprise PKI, compliance identity, active TLS revocation, or hostile-multitenant isolation |
| Serve the service | Caddy, Traefik, NGINX Proxy Manager, application TLS | **Fact:** Provide a lightweight rustls TLS terminator or supply certificates through files and ACME | Mature reverse proxies continue to own advanced HTTP routing, middleware, authentication, public ingress, and edge policy |
| Reach it from elsewhere | Tailscale, Headscale, NetBird, VPN, subnet router | **Inference:** Koi supplies service-level names and trust once packets can reach the site; split DNS can send `.internal` queries to Koi | Koi does not create a WAN overlay, traverse NAT, relay traffic, or provide user/device access policy |
| Observe and automate | Prometheus, scripts, OpenAPI clients, AI-agent hosts | **Fact:** Export Prometheus HTTP-SD, DNS-zone views, CLI/HTTP/OpenAPI surfaces, and MCP tools/resources | Koi supplies current local control-plane state; it is not a metrics database, SIEM, workflow engine, or autonomous security authority |

**Inference:** The strongest adoption story is not “replace your stack.” It is “keep the tool that already owns each neighboring concern, and stop hand-wiring service identity between them.” This matches Koi's documented doctrine to export their formats, consume existing labels, and remain easy to leave. Source: [README: works with your stack](../../README.md#works-with-your-stack).

## Comparable projects

| Project or stack | Classification | Documented overlap | Where it wins | Where Koi can credibly differ |
| --- | --- | --- | --- | --- |
| Bonjour / Avahi + local DNS + Caddy/Traefik + `mkcert`/step-ca | **Direct behavioral substitute — Inference** | Together these provide local discovery, private names, certificate trust, issuance, and serving | Mature point solutions, independent replacement, large existing knowledge base | One shared service lifecycle, one cross-platform artifact, account-free offline operation, and less reconciliation among catalogs, zones, CAs, and routes. Primary sources: [Apple Bonjour](https://developer.apple.com/bonjour/), [Avahi](https://avahi.org/), [Caddy local HTTPS](https://caddyserver.com/docs/automatic-https), [mkcert](https://github.com/FiloSottile/mkcert), [step-ca](https://smallstep.com/docs/step-ca/) |
| HashiCorp Consul | **Closest single functional competitor — Inference** | Service catalog, DNS, health-aware discovery, CA-backed mTLS, APIs, multiple runtimes | HA control plane, multi-datacenter and hybrid-cloud operation, service intentions, traffic management, Envoy ecosystem | Trusted-LAN simplicity without a Raft server cluster or sidecar data plane; human/browser-facing local names and trust as the first outcome. Sources: [service discovery](https://developer.hashicorp.com/consul/docs/discover), [architecture](https://developer.hashicorp.com/consul/docs/architecture), [service mesh](https://developer.hashicorp.com/consul/docs/connect) |
| Tailscale MagicDNS + Serve | **Adjacent and partially substitutive — Fact/Inference** | Stable device names, HTTPS certificates, private service proxying, identity-aware access | Cross-WAN reachability, NAT traversal, user/device identity, access grants, polished clients | Koi names arbitrary LAN services and unmanaged local devices without requiring them to join an overlay or use a coordination account. Tailscale documents that MagicDNS names devices, arbitrary records cannot be added, and Serve names are restricted to the tailnet domain. Sources: [MagicDNS](https://tailscale.com/docs/features/magicdns), [DNS](https://tailscale.com/docs/reference/dns-in-tailscale), [Serve](https://tailscale.com/docs/features/tailscale-serve), [control/data planes](https://tailscale.com/docs/concepts/control-data-planes) |
| Headscale | **Adjacent self-hosted substitute — Fact/Inference** | Self-hosted Tailscale control plane, MagicDNS, extra A/AAAA records, tailnet policy | Self-hosted overlay reachability for hobbyists and small organizations | Koi requires no externally reachable control server and concentrates on services within an already reachable LAN. Headscale still requires a public HTTPS server for normal deployment. Sources: [design goal](https://headscale.net/stable/), [DNS](https://headscale.net/stable/ref/dns/), [requirements](https://headscale.net/stable/setup/requirements/) |
| NetBird | **Adjacent and converging competitor — Fact/Inference** | WireGuard mesh, peer DNS labels, access policy, private/public reverse proxy with automatic TLS | Remote reachability, user/machine authorization, relays, public exposure, SSO; its reverse proxy now covers HTTP and L4 services | Koi remains local-first, account-free, and usable without management/signal/relay infrastructure or a public domain. NetBird's reverse proxy was beta at verification time. Sources: [architecture](https://docs.netbird.io/about-netbird/how-netbird-works), [DNS labels](https://docs.netbird.io/manage/dns/extra-dns-labels), [reverse proxy](https://docs.netbird.io/manage/reverse-proxy) |
| Caddy | **Point competitor and high-value complement — Fact** | Local CA, trust installation, automatic HTTPS, reverse proxy, embedded ACME server | Exceptionally mature HTTPS automation and HTTP serving | Koi adds network discovery, shared node enrollment, DNS, health, runtime lifecycle, and service exports. Koi should not compete on general web-server breadth. Sources: [automatic HTTPS](https://caddyserver.com/docs/automatic-https), [ACME server](https://caddyserver.com/docs/caddyfile/directives/acme_server) |
| Smallstep `step-ca` | **Point competitor and future trust complement — Fact/Inference** | Private X.509 CA, ACME, automated renewal, enrollment provisioners | PKI depth, policies, OIDC/cloud identity, HSM/KMS integrations, SSH certificates, and mature HA options | Koi makes local service identity the workflow and bundles discovery/name/serve; Smallstep should own deployments whose primary requirement is PKI. Sources: [step-ca](https://smallstep.com/docs/step-ca/), [integrations](https://smallstep.com/docs/step-ca/integrations/) |
| Kubernetes + CoreDNS + cert-manager | **Cluster-scoped substitute — Fact** | Service discovery/DNS and certificate automation for orchestrated workloads | Declarative scheduling, cluster identity, scaling, policy ecosystem | Koi serves heterogeneous LAN clients and workloads outside a Kubernetes trust and network boundary. Sources: [Kubernetes Services](https://kubernetes.io/docs/concepts/services-networking/service/), [cert-manager Certificates](https://cert-manager.io/docs/usage/certificate/) |
| Istio, Linkerd, SPIRE | **Upmarket boundary, not target — Fact** | Workload identity, mTLS, service-to-service security and traffic handling | Fine-grained attestation, authorization, transparent data plane, telemetry, policy | Koi's trusted-LAN and browser/service-name workflow is intentionally smaller. Sources: [Istio](https://istio.io/docs/concepts/what-is-istio/), [Linkerd automatic mTLS](https://linkerd.io/docs/features/automatic-mtls/), [SPIRE concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/) |

**Inference:** The market whitespace is between raw Zeroconf/point tools and remote-first or enterprise service networking. The main incumbent is a hand-assembled stack, while the main strategic threat is adjacent networking products continuing to bundle DNS, certificates, and proxying.

## Strategic openings

- **Fact:** ICANN permanently reserved `.INTERNAL` from delegation for private-use applications in July 2024. **Inference:** Koi's default namespace now has a stronger legitimacy and collision story than ad hoc `.lan`, `.home`, or `.corp` choices. The reservation does not make operating systems route it to Koi automatically. Source: [ICANN Board resolution](https://www.icann.org/en/board-activities-and-meetings/materials/approved-resolutions-special-meeting-of-the-icann-board-29-07-2024-en).
- **Inference:** The sharpest whitespace is the “last meter” between a service that is running and a person or device that needs a stable, browser-trusted URL on the same network.
- **Inference:** Koi's most defensible system property is one service record feeding multiple consumers. Point tools can reproduce each feature; fewer can prevent DNS, certificate, health, proxy, and runtime views from drifting because they derive from the same lifecycle.
- **Inference:** The container-to-LAN bridge is a strong wedge. Docker documents that its automatic DNS works inside user-defined networks and that published ports are required outside them; Koi can translate container metadata into a LAN identity without modifying the image. Source: [Docker bridge networking](https://docs.docker.com/engine/network/drivers/bridge/).
- **Hypothesis:** Account-free, internet-independent operation is especially valuable for privacy-sensitive homelabs, temporary developer networks, classrooms, labs, workshops, and disconnected edge sites. Validate these segments separately rather than treating “offline” as one market.
- **Owner choice:** Compete through interoperability. Preserve Caddy/Traefik for advanced serving, AdGuard/Pi-hole for DNS filtering, Tailscale/NetBird for remote reachability and access policy, Prometheus for observability, and Smallstep/SPIRE for higher-assurance identity.
- **Owner choice:** Treat MCP as a differentiating management surface after the core outcome works. “AI can inspect and operate the local service catalog” is useful; “AI-native networking platform” would obscure the primary job and increase security scrutiny prematurely.
- **Fact/Inference:** The owned Koi page already expresses the right adoption sequence—look before setup, name what matters, then share current truth—and carries explicit choose-elsewhere boundaries. The near-term opening is therefore distribution consistency: link that page from GitHub metadata and make release, registry, and community surfaces reuse its promise rather than inventing competing category language.

## Risks and dependencies

| Risk or dependency | Type | Market consequence | Required posture |
| --- | --- | --- | --- |
| Category confusion with VPN, service mesh, reverse proxy, or enterprise PKI | **Positioning risk — Inference** | Users compare Koi against products with WAN transport, identity policy, advanced routing, HA, or compliance and conclude it is incomplete | Lead with the trusted local URL outcome and publish explicit “works with / not for” boundaries |
| Tailscale and NetBird continue bundling service DNS, certificates, and proxying | **Competitive risk — Fact/Hypothesis** | Remote-first products can absorb users who also need LAN naming; NetBird's reverse proxy was already beta in July 2026 | Own offline/local unmanaged-device workflows and make split-DNS collaboration excellent rather than attempting an overlay |
| Caddy, Smallstep, Consul, and Kubernetes are mature in their specialties | **Substitution risk — Fact** | A user whose problem is primarily HTTPS, PKI, service mesh, or cluster discovery will select the specialist | Qualify users early and make migration/export straightforward |
| Root-CA distribution and token-protected management | **Security risk — Fact** | A trust failure damages the entire category promise; plaintext remote management can expose a bearer token | Keep loopback default, document TLS-protected remote access, audit key custody/enrollment/recovery, and avoid unqualified security claims |
| Multicast, port 53, firewalls, VLANs, guest isolation, and overlay routing | **Environmental dependency — Fact** | The demo can work on one LAN and fail in realistic segmented networks or collide with an existing resolver | Publish a supported topology matrix, conditional-forwarding recipes, port-conflict diagnostics, and gateway/multi-subnet guidance |
| OS and browser trust-store fragmentation | **Platform dependency — Fact** | A root installed in the system store may not automatically cover every browser, mobile device, Java runtime, or container | State the exact supported stores and make `trust diagnose` explain gaps; Caddy and mkcert document the same class of limitation ([Caddy](https://caddyserver.com/docs/running), [mkcert](https://github.com/FiloSottile/mkcert)) |
| Pre-1.0 breaking changes and broad support surface | **Maturity/capacity risk — Fact/Inference** | Early adopters may become support-heavy and integrations can drift | Keep the warning prominent, constrain the supported matrix, publish upgrades, and prefer hardening or subtraction over new domains |
| Runtime startup reconciliation, Docker reconnect, embedded data-root consistency, and detached session lifecycle | **Implementation risk — Fact from repository analysis** | The core “automatic lifecycle” promise can fail silently after restart or backend interruption | Repair and regression-test before using reliability or self-healing language in adoption material |
| `.internal` reservation misunderstood as automatic resolution | **Education risk — Fact/Inference** | Users expect the name to work without configuring a resolver or DHCP/split DNS | Say “collision-safe private namespace” rather than “universally resolvable”; show resolver configuration as part of activation |
| Telemetry temptation conflicts with local-first trust | **Adoption-measurement risk — Hypothesis** | Cloud analytics could undermine the privacy/offline value proposition | Prefer opt-in, aggregate, privacy-preserving community evidence and local diagnostics; never make core operation depend on telemetry |

**Owner choice:** The ecosystem strategy is additive: Koi should be easiest to adopt where it can sit beneath an existing stack, easiest to diagnose when a boundary is misconfigured, and easiest to remove without taking the user's DNS, proxy, PKI, or observability system with it.

## Adapter priorities

- **P0 — make present claims true:** repair gap-free Docker/Podman reconciliation and reconnect; correct Caddy/Traefik backend-versus-listener semantics; make private ACME usable through standard clients/challenges; split real Prometheus metrics endpoints from blackbox probes; add scoped Tailscale/Headscale client and record CIDRs; and exercise every advertised partner with real containers or clients.
- **P1 — open the highest-value doors:** add a generic external ACME issuer for step-ca/Smallstep; publish tested CoreDNS, Headscale, Pi-hole v6, and AdGuard delegation recipes; add reversible split-DNS helpers; expose which component owns DNS, proxy, PKI, and monitoring; and diagnose duplicate mDNS responders and port conflicts.
- **P2 — demand-driven expansion:** consider an opt-in Kubernetes Service/Gateway reader, read-only Consul catalog ingest, and a Home Assistant diagnostics/add-on surface only after demand is observed. Defer SPIFFE integration and Avahi D-Bus emulation until a concrete use case justifies their complexity.
