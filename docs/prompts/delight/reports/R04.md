## Task and selected slice

Build the one composition-owned projection that correlates authoritative mDNS,
runtime, DNS, Health, Proxy and CertMesh evidence into coherent devices,
services, endpoints, conditions and actions. Preserve provenance, scope,
freshness and ambiguity, and make dashboard, embedded and automation
presentations consume the same immutable snapshot.

## Plan / exact owner and changed files

- `koi-common::service` owns schema-1 opaque IDs and dependency-light catalog
  DTOs. `koi-config::installation` owns atomic UUIDv7 installation identity at
  `state/installation.json` and fails closed on corrupt/future documents.
- `koi-compose::catalog::ServiceCatalogRuntime` is the sole model owner. It
  subscribes before reading sources, retains bounded evidence, fences source
  revisions, derives versioned SHA-256 IDs, and is joined by the composition
  lifecycle. `cores.rs`, `status.rs` and `snapshot.rs` wire that runtime into one
  aggregate product snapshot.
- `announce.rs` stamps Koi-owned HTTP and MCP advertisements with the durable
  installation ID and distinct role-stable service IDs.
- `koi-serve::inventory` and dashboard serialization project the same
  `KoiStatus.catalog`; three serve fixtures gained only the additive aggregate
  field. `koi-embedded` gained only the exhaustive installation-error mapping.
- Architecture coverage, the shared utility index and CONTRACT owner map were
  updated. No frontend cache, domain-private persistence read, generic event bus
  or second catalog state machine was introduced.

## Before -> after

- Before: each presentation could expose specialized domain snapshots, but no
  authoritative Device/Service/Endpoint model or durable installation identity
  existed. Correlation, freshness, ambiguity and action eligibility had no
  common owner.
- After: explicit installation/service IDs take precedence, then durable
  source identity, then an exact normalized endpoint and compatible kind on a
  proven device. Similar names never merge by themselves; conflicting explicit
  identities remain separate and ambiguous.
- Before: a closed source could be mistaken for empty current truth. After:
  source loss retains evidence as stale/source-unavailable for ten minutes,
  while an explicit newer full snapshot withdrawal becomes Absent. Lower source
  revisions cannot resurrect a withdrawn entry.
- Before: endpoints had no catalog-wide action policy. After: only current,
  unambiguous HTTP(S) endpoints with a concrete browser-usable destination may
  offer Open. API-only/unknown TCP, wildcard binds and unzoned IPv6 link-local
  endpoints retain connection/detail/diagnosis actions without an invented Open.
